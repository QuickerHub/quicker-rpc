# QuickerAgent 产品设计

QuickerAgent 是面向 Quicker 动作维护与工作区任务的 Agent 工作台。用户在同一会话中提出需求、查看工具进度、处理审批，并通过已有资源与浏览器面板检查结果。产品当前能力与可用范围见 [产品功能地图](../docs/product/README.md)。

## 工作台体验

主界面沿用 Quicker V2 Agent 工作台的视觉设计：平坦的中性灰深浅主题、紧凑窗口栏、左侧工作区与会话导航，以及居中的对话内容和输入区。

参考源为 Quicker 仓库的 `QuickerPc/Quicker.Headless/Web/src/features/agent/sdk/AgentShell.tsx`、`features/agent/agent-workspace.css` 和 `src/theme.css`；迁移的是 Agent UI SDK 的布局与视觉约定，功能范围仍由本产品的能力地图定义。

- 顶栏高 36px，展开侧栏宽 240px；正文与输入区共享最大 960px 的内容轨道。
- 对话正文为 14px，代码为 12px；主界面、菜单、浮层与设置共用黑白灰主题 token，选中、焦点与发送按钮使用单色对比。深浅主题均可读，状态提示与代码高亮保留语义色。
- 新会话将输入区与引导内容居中；窗口较矮时内容可滚动，输入与发送操作保持可达。
- 已有会话、工具消息、审批、输入与侧面板保留各自行为。界面迁移不改变 Agent/Ask/Launcher 的权限含义。
- 设置、资源、浏览器与小窗快捷入口继续打开已有功能；工具测试与发布预览遵守现有开发/调试门控。

主工作台布局限定于 `agent-workbench` 作用域；通用配色在主题根节点定义，让挂在 `body` 下的浮层保持一致。Launcher 的透明窗口与动作设计器的独立主题继续遵循各自的使用场景。

## 扩展原则

工作台为后续功能保留清晰的组合边界：外壳承载导航与主区域；会话框架组合标题、消息、审批、输入和 dock。业务组件继续使用现有会话、工具、持久化与执行服务。

快捷入口通过声明式功能定义描述名称、目标和可用条件，再由界面绑定已有面板、命令或路由。新增入口必须对应可用能力；界面定义不授予工具权限，也不替代运行时 capability 判断。

DeepSeek Harness 的布局组合和静态描述与运行状态分离是架构参考。工作台仍使用现有 AI SDK Agent 内核与消息流，扩展入口的工程约定见 [Agent 架构](../docs/agent-architecture.md#工作台组合边界)。

后续优先将服务与展示边界落到代码，再扩大面板抽象。桌面优先的目标是静态 React 界面、
独立 Node Agent service 与薄 Electron 壳；Next.js 当前承担兼容宿主，不作为产品能力约束。
替换 UI 构建工具要保持会话、审批、Launcher 和 Designer embed 的现有交互，迁移门槛见
[架构目标](../docs/agent-architecture.md#框架去耦与目标运行边界)。

## Agent 运行与会话原则

- Agent、Ask、Launcher 和命令限制由最终可执行能力集共同约束；界面选择或子代理不能扩大父任务的权限。显式禁用所有工具与未配置工具是两种状态。
- Ask 当前不开放浏览器工具：现有观测调用也可能启动 runtime 或创建会话；须先提供只连接已有会话、无导航与宿主启动副作用的观测端口，再按能力逐项开放。Agent 模式保留浏览器能力。
- 停止操作属于当前运行，会取消它的模型、压缩与派生工具工作，并释放该运行拥有的连接。切换会话允许原会话继续在后台执行，不等同于停止。
- 会话运行状态、用户草稿、工作台布局和工具展示各有唯一 owner；展示方式改变不应丢失正在运行的任务、审批或未保存内容。
- 隐藏面板不能抢占全局快捷键；菜单和弹层应支持键盘进入、关闭和焦点恢复。
- 读回已有历史、展示工具详情和准备模型上下文是不同投影，不为换皮另建一套 send、审批或历史存储协议。
- 清理临时工作区只删除该目录的本地文件；导出文件中的动作或子程序 ID 不构成宿主对象的所有权证明，不能据此自动删除 Quicker 内容。

长期重构的阶段、依赖和验收状态统一维护在 [产品计划](../docs/product/README.md#agent-与工作台持续重构)。这些原则是整改目标，不能据此宣称现有实现已经全部满足。

## 范围与待确认决策

语音输入、语音聊天与剪贴板历史已移除，不属于工作台功能范围。

当前已实现的迁移覆盖主 Agent 工作台与已有功能入口。现有 V1 动作 YAML 流程通过 Agent 的 open/save 工具与原文件工具接入同一会话，沿用 CLI/MCP 的 bundle、基线和冲突保护；目前尚无新的设计器面板。第三方动态 UI 插件和可替换 Agent 执行器尚无已确认的产品交互。

## 统一动作设计器（已确认目标，待实现）

下一项界面交付搬入 Quicker 项目的新版动作设计器。复用其 React 组件、动作模型、步骤
catalog、编辑会话和 host bridge 语义；沿用本工作台的黑白灰深浅主题。通过 adapter 连接
V1/V2，展示和编辑组件不按版本复制。

- 一个兼容宿主可自动连接；多个宿主可用时明确选择，编辑会话展示并绑定目标。断连、重启
  或连接变化不能把未保存内容写到另一个实例。
- 载入完整动作，覆盖来源设计器已有的步骤/参数、变量、资源和嵌套结构；保留选择、撤销/
  重做、脏状态、校验与错误反馈。迁移按能力清单验收，不能只搬视觉外壳。
- 模块/动作/子程序 catalog 与外置脚本/默认值文件分别验收；保留 qkrpc 现有文件资源能力。
  连续多次编辑后，保存必须与当前可见文档一致，不能从陈旧的父组件副本写回。
- 编辑会话持有唯一文档 controller；人工与 Agent 修改进入同一文档版本流程，不各保留一份
  可静默覆盖对方的草稿。保存共用 storage identity、revision、宿主内存态保护和部分落盘反馈。
- Agent 继续使用现有单一 AI SDK loop 和权限。设计器的 UI catalog 可以读取 UI schema；
  Agent 仍使用压缩 step-runner schema，不通过迁移扩大工具权限。
- 先跑通已有通信契约的完整编辑链，再用真实负载研究传输效率；不为搬界面同时重写协议。

自动识别、双宿主、Agent 整合与通信优化的依赖/验收统一见 [主线计划](../docs/product/README.md#统一-rpc-与动作设计器当前主线)。
